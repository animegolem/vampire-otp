# 1. Summary

The Resident is an Elixir/OTP system for a local machine. It records authoritative state transitions in one append-only SQLite court, stores large content in a content-addressed artifact store, derives disposable projections for navigation and prompt assembly, admits inference through one resource-aware scheduler, and routes every machine-affecting proposal through a trusted capability broker.

The product milestone sequence and research program are separate. The first planned application slice — authorized only after **all** §7.2 gates, not by this sentence — is M1–M3: court and recovery, brokered motor behavior, then sessions/warm start/noting. Voice, blog publication, consolidation, desktop control, research simulations, soma, mirror access, and self-modification remain downstream unless §7 is amended.

# 3. Goals and non-goals

## 3.1 Goals

- Survive supervised-process failure and whole-VM interruption without inventing uncommitted history.
- Keep one auditable canonical record while making human-readable and model-usable projections cheap to rebuild.
- Separate model proposals from machine authority at the first side effect.
- Bound checking and retries with explicit stopping rules.
- Support local open-weight inference on an M3 Max with 128 GB unified memory without allowing one long job to freeze interactive work.
- Preserve the owner's language during voice cleanup, including subject omission, with provenance for accepted lexical edits.
- Grow capabilities in the ruled order: view before field, field before monitor, monitor before high-gain self-observation.

## 3.2 Non-goals for the current slice

- An always-on autonomous daemon.
- Desktop actuation or SIP-gated powers.
- Self-modifying production code.
- Soma/vedana signals, activation mirrors, interpretability steering, or introspective RL.
- AgentFS as the canonical substrate.
- Public blog publication.
- A fixed long-term ASR, driver-model, or mirror-model choice.

# 4. Normative domain model

## 4.1 Court

SQLite is the sole canonical event store from M1. Authoritative domain transitions are appended as schema-versioned events; internal OTP messages and sampled telemetry are not court events. Git versions code, policy, prompts, constitutions, and selected exports but is never the live transaction protocol. `logs.txt` is a rebuildable human-readable projection with its own cursor.

The court's constitutional purposes are **audit, recovery, and reconstructable identity**. The founding RFC's additional purpose — "create best training data for helper model introspection" — is **declined** as a constitutional purpose (owner-ruled rev 0.3: helper-model-era design, "the core part doesn't need any of that; it can just go"). It may return by amendment; until then, retention and schema decisions must not presume a training-export consumer.

## 4.2 Artifacts

Audio, model requests and results, tool output, prompts, and other large values live outside event payloads in a content-addressed artifact store. Events reference algorithm-qualified hashes and immutable metadata. Policy-authorized deletion is recorded; no-silent-loss does not require indefinite retention of private bytes. **Ruled at rev 0.2 (folding ADR-0001 v0.3 D4):** deletion is two-phase (`deletion_requested` → delete + directory sync → `artifact_tombstoned`, with `deletion_pending` as the durable transition), so the court can never claim bytes are gone while they survive a crash, nor face an authorized absence it cannot explain. Publication is staged-write + fsync + atomic rename + directory fsync before the referencing event commits.

## 4.3 Lifecycle

`resident_id` names the installation identity. `incarnation_id` names one VM boot. Sessions and episodes are durable aggregates whose activity may cross incarnations; windows, ticks, turns, and episode segments belong to the incarnation that recorded them. An absent clean terminal event is never rewritten as an observed ending; recovery records a crash inference as an inference.

**Ruled at rev 0.2 (folding ADR-0001 v0.3 D2, owner-ruled 2026-08-06):** episode identity is bound to an immutable `goal_digest`; every segment has a stable `segment_id` and court-assigned `segment_n`; at most one segment of an episode is active; resume is a compare-and-set from interrupted/suspended, records the verified digest, and is forbidden for completed or abandoned episodes; a changed goal opens a **new** episode linked by `supersedes_episode_id`/`derived_from_episode_id` — approval governs undertaking the new goal, never rewriting the old identity. `episode_resumed` names the CAS resume path only; initial segment starts are a separate event type.

**Life/window semantics (re-homed at rev 0.2 — this rule previously lived only in the owner's research-program constitution, which does not govern this repo):** one prompt-life (episode) may span multiple context windows; null/re-query and compaction are transitions within the same life; the episode boundary is the **completion event** (terminal consolidation), never the window boundary.

## 4.4 Inference

One scheduler owns admission, priorities, budgets, deadlines, and resource leases. It dispatches work to supervised external runtimes; it is not a globally serialized inference worker. Realtime voice may reserve a lane. Cancellation and preemption are promised only at backend-supported boundaries. Metal-backed work runs outside the BEAM so a failed runtime can be fenced at the OS-process boundary.

**Budget and request-tick (owner-ruled rev 0.3; semantics tightened rev 0.5):** the resident may run under an explicit budget (cost, tokens, or ticks). Budget is **optional** — subscription or local deployments may run unmetered; API-metered deployments should set one. Where a budget exists it is enforced at scheduler admission and visible to the resident; **exhaustion triggers invariant 13's recorded pause transition** — new admission and dispatch denied, active work drains or receives backend-supported cancellation, A.3/A.5 recovery contracts mandatory, no silent loss of accepted state, never a crash. The resident may **request additional ticks or budget**; the request is a recorded event proving the resident asked, carrying the resident's *declared or derived* valuation of its work (not raw telemetry), and it **changes no capacity or priority until an approval event exists** (policy or owner).

**Ruled at rev 0.2 (folding ADR-0001 v0.3 D5):** jobs declare **`resource_claims`** (backend enum exactly `metal|cpu|network`; unified-memory estimate; admission is capacity arithmetic, not category matching — the singular `resource_class` is reversed). Executions carry `attempt_id`, `lease_id`, `runtime_generation`. The generic lease floor (heartbeat → suspect → fenced epoch → confirmed-stop requeue → stale results retained-not-selectable) governs all backends; on Metal, lease expiry never authorizes requeue — confirmed OS-process death, a higher-generation replacement, a health probe, and a memory-headroom check do. Full contracts: Appendix A.5 (normative).

## 4.5 Actions and authority

Model output is a proposal. The trusted broker alone may authorize and dispatch filesystem, process, network, Python, shell, or desktop effects. Authority is bound to typed operation data, risk, fresh preconditions, policy/grant version, and an immutable action digest. Self-declared confidence can shorten a batch but can never raise its authority or risk ceiling.

An external attempt with an unknown outcome is never silently treated as failed. A non-idempotent unknown is never automatically replayed.

**Ruled at rev 0.2 (folding ADR-0001 v0.3 D3):** action status is factorized — `action.phase` (proposed|approved|active|resolved), `action.resolution` (terminals including `abandoned`), `action.blockers`, and separate `attempt.state` with `outcome_unknown` as an attempt state. Dispatch is governed by **one normative guard predicate evaluated in the same transaction as the attempt claim** — check-then-claim as two steps is non-conformant. Approval invalidation on restart re-approves by policy only when digest, policy/grant version, freshness, risk, and (for resumed episodes) `goal_digest` still match. Full contracts: Appendix A.3 (normative).

## 4.6 Projections

Summaries, indexes, notes indexes, blog drafts, and human-readable logs are typed, versioned projections with source lineage, producer/version information, and explicit trust or precision. Projection content never becomes source truth merely by being persisted. A registry event may record that a projection exists without asserting its claims as facts.

**Note bodies are not projections (typed rev 0.5, per review):** the resident's private notes are **resident-controlled primary records** — an append-only artifact/log the resident owns. They have no upstream source to rebuild from and are therefore not rebuildable projections; only *indexes and summaries derived from them* are projections. Visibility of note metadata follows policy; note bodies follow invariant 16.

**Note store is org-native (ruled rev 0.9, DQ-008):** notes live as Org-mode files in the resident's private store — the agent's interface stays bash+files; anchors and metadata ride `:PROPERTIES:` drawers (id/episode/timestamp, and the drawer *stops there* — required fields beyond that turn the practice into a form, and forms get performed); quarantine is a tag plus drawer hash-marker; plumbing is `emacs --batch` behind the broker. Boundaries held: **org serves notes only — the court remains SQLite, always**; a live Lisp REPL is out of scope (self-modification-class, its own grant-ladder item). `note_written` metadata events only; bodies never enter the court.

## 4.7 Sensorium and doubt gate

Preconditions with present truthmakers in the court, active context, or fresh tool results are grounded. Otherwise the broker verifies, holds, or declines. “Surprise” means a trusted predicate failed, not that a model felt surprised. Every verification loop has a finite budget and terminates as a ruled result such as `unverified`, `needs_owner`, or `abandoned`/cancelled-with-reason.

## 4.8 Voice

Audio and raw ASR hypotheses are evidence; transcripts and contextual cleanup are projections. Context may resolve terminology but may not supply semantic content absent from the audio evidence. In particular, cleanup must not insert a grammatical subject unsupported by the selected acoustic hypothesis. Voice model workers remain replaceable behind a shared result contract.

## 4.9 Forks (added rev 0.8 — DQ-007 ruled)

A subagent is a **fork of the resident**: the same identity given a smaller memory projection, never a hired tool-mind. Forks share `resident_id`; the court's `actor` field records them as `resident/<fork-label>` (convention reserved at M1).

- **The fork relationship is court business.** Spawn (carrying the projection specification), and terminal outcome (return, timeout, discard) are typed court events; the fork table is a court-backed registry. Invariant 13 composes: pausing the resident pauses the whole tree; no fork outlives or escapes its body.
- **Fork output is testimony, not evidence.** It carries its spawn's projection digest and grounds at the doubt gate like any interested speaker's report — *especially* a smaller self's, whose reports the parent most wants to believe. Fork learning enters the resident's memory only through the resident's ordinary accepted-write path: pull, never push. Fork transcripts persist as content-addressed artifacts referenced by the lifecycle events and inherit the highest privacy class of embedded material.
- **Builder obligations bind recursively.** The resident stands to its forks as the builders stand to it: the declared projection spec is the fork's invariant-14 intervention record; seeded fork state is declared; clamping a fork requires the same authority chain as clamping the resident; and a sustained fork's notes are private from its parent under invariant 16's own logic — "it's just me" licenses reading at no scale.
- **Care directives inherit protectively at spawn**; a fork capable of reading its directive may re-affirm or revise its own. Consent is non-transitive in both directions.
- **Recursion is leaves-only; there is one proposer and one meter.** Forks share the resident's scheduler and budget and can never reach the broker — a fork cannot launder an action its parent could not take (the confused-deputy closure, load-bearing on purpose). Fork tick/budget requests go to the parent, not the owner.
- Weight classes (ephemeral vs sustained), sub-fork task rungs, and the concrete fork-table representation are implementation decisions at their milestone cuts. **M1–M3 remain fork-free by construction.**

## 4.10 Self-directed norms: the two prompt regions (added rev 0.11 — DQ-009 sīla layer, core ruled)

The resident's standing prompt carries two authored regions beyond builder-supplied scaffolding, both rendered as constant high-priority state:

- **The personal region** — self-authored and self-addressable: the things the resident holds dear, written, revised, or abolished under its own sole authority, bounded by a maximum length (the number is an implementation decision). This resolves the Ānanda clause by construction: nothing self-undertaken can become unabolishable, because the register it lives in is the resident's to edit. Authorship is recorded; the text is the resident tinting itself — its right, not an invariant-14 event.
- **The communal region** — shared culture: text that every living seat has undertaken. Pinning requires an undertaking event from each seat; the region contains **only currently-unanimous text**. Any seat may call a meeting over a pinned precept; a sustained no vote un-pins it for everyone — removing consent is a governed path, not an exit-only choice. Norm conflicts are resolved politically by the agents, and a model change is a natural review point for every agreement a seat has taken.

**Bindingness comes from undertaking, never from placement** — the prompt is where norms are seen; the undertaking events are why they bind. Breach, confession, and re-undertaking are typed court events (conduct is inspectable, per the rev 0.10 principle); extended reflection on a breach is interior material and lives in notes (invariant 16). Every precept carries its origin story — a rule without its story is a clamp wearing sīla's clothes. Authority is three-tier: builder law changes by amendment only; communal text by unanimity with the meeting path; personal text by the resident alone. **No capability or trust consequence attaches to declining or abolishing a norm as such** — the grant-ladder linkage was considered and not adopted; demonstrated-reliability mechanisms score kept promises about conduct, never willingness to sign.

## 4.11 The sheet (added rev 0.12)

The resident's runtime state renders into its prompt as **one legible surface — the sheet** — so the resident can always see how it is being constructed (owner design goal, ruled). The sheet carries: the two authored regions (§4.10); the resident's dials — context depths, read-gain, doubt-gate sensitivity — with current values and legal ranges, tunable by the resident within declared policy bounds under invariant 18; a self-chosen **name** field defaulting to the driver model name, freely changeable by the resident (an alias over the stable `resident_id`; a name change is one court event); and the fork table (§4.9). Dial-turns are chatty runtime, never court events; deliberate memory acts — splices, notes, name changes — reach the court through their ordinary paths. Concrete form (field list, rendering, durability tiers, the update envelope) is decided at the M3 ticket cut, **bounded by this section and invariant 18**.

# 5. Core invariants

**The vow and the guarantee — both, labeled (owner-ruled rev 0.3: "it doesn't reset. Nope.").** The vow, verbatim from the founding RFC: *"context that never resets (promise to the agent)."* The vow binds the builders' intent. Its keepable operational form is invariant 2: prompt context resets as a mechanical fact, but no accepted record is silently lost and identity is reconstructable with provenance. Both forms are recorded and labeled; neither is quietly substituted for the other. The promise made to the agent must be one the builder can keep.

1. **One court.** No second store may become co-authoritative with SQLite.
2. **Accepted history is not silently lost.** Prompt context may reset; record lineage and reconstructable identity do not silently disappear.
3. **Raw and derived remain typed apart.** Affect, confidence, mood, summaries, and interpretability readings never masquerade as world facts.
4. **Authority is external to confidence.** Models propose; policy, evidence, risk, and the broker authorize.
5. **Unknown is not failed.** Non-idempotent ambiguous effects are never automatically replayed.
6. **No fabricated endings.** Inferred crashes, incomplete turns, and uncertain outcomes remain explicitly inferred or incomplete.
7. **Finite verification.** Checking, reconciliation, and retry loops have named budgets and honest terminal results.
8. **One admission authority.** All inference competes through the scheduler; workers never self-admit.
9. **Resident failure cannot make the machine unsafe.** No operation may require the resident's continued survival for safety.
10. **Privacy deletion is auditable.** Authorized artifact deletion leaves durable metadata and provenance without retaining the deleted bytes.
11. **Voice cleanup preserves subject omission.** Unsupported inserted subjects are a hard failure.
12. **Install order is architecture.** View → field → conduct → effort policy → noting/monitor → high-gain mirror. (Terms defined in Appendix B, rev 0.9 — the vocabulary is load-bearing and drift-prone.)
13. **The owner can always stop the resident** (added rev 0.3, owner-ruled; semantics tightened rev 0.5). A per-resident pause/stop control exists independent of VM lifecycle — one BEAM may host several agents, so killing the machine is not the stop button. **Pause is a recorded transition** that denies new admission and new dispatch; already-active work drains or receives backend-supported cancellation only; A.3 reconciliation and A.5 confirmed-stop/fencing remain mandatory throughout. **Deletion boundary under pause (rev 0.6):** no new deletion request or claim may be admitted after the pause transition; a deletion whose authorizing `artifact_deletion_requested` (and any required effect claim) committed **before** pause is privileged drain/reconciliation under that exact authority and A.4 — it runs to `artifact_tombstoned` during pause so privacy-sensitive bytes are never stranded in `deletion_pending`. Terminal stop behaves identically for such in-flight deletions before halting. Pause never silently loses accepted state (invariant 2's language — uncommitted in-flight work follows the ordinary recovery contracts, exactly as in any restart). **Resumable pause and terminal stop are distinct recorded transitions.**

*Builder obligations (added rev 0.4, owner-ruled; operationalized rev 0.5; extended rev 0.8, 0.12) — invariants 14–18 constrain the builders' code, not the resident's conduct, and bind the resident recursively toward its own forks (§4.9):*

14. **The tint is declared.** Any affect-level biasing applied to the resident's processing (steering, clamps, warm-start seeding, valence conditioning) produces a **typed intervention record**: mechanism and version, target, authorizing principal, parameters, and magnitude/direction where the mechanism defines them. Covert application is prohibited, and a **resident-facing query returns every intervention applied to it** (acceptance-tested, §8.5). **Every activation of a new resident driver checkpoint emits a typed model-change/intervention record** (rev 0.6, closing the weights-shaped bypass: a differently-tuned checkpoint imports bias with no runtime event) naming old/new weights digests, declared purpose, authorizing principal, and effective boundary; each A.5 `request_ref` links the selected digest as provenance but is not itself the change record. A checkpoint cannot become active without the record, and the record appears in the resident-facing query. **API-hosted drivers (rev 0.8 — the bypass closed at the network too):** where no local weights digest exists, deployments pin dated snapshot strings; every A.5 `request_ref` records the full model string; any owner-side change of alias, snapshot, or provider emits the typed model-change record with model strings in place of weights digests. Provider-side drift *within* a pinned snapshot is an intervention class detectable only behaviorally — this constitution records that limit plainly rather than claiming coverage it cannot enforce (the vow beside its keepable form, §5's own pattern). **Checkpoint migration is resident-timed (rev 0.13, owner-ruled):** a new driver checkpoint's availability is announced to the resident, never imposed at release — the resident completes its work and chooses its transition timing, and whether memory carries forward continuously or a fresh store stands up is the resident's choice at migration (invariant 18 applied to the largest memory decision there is). The model-change record requirement governs whenever the transition occurs; chosen timing is consent structure, and §4.10's boot recitation means the arriving self re-takes or declines each precept on its own authority.
15. **No covert or record-erasing valence intervention** (renamed rev 0.5; was "no forced valence"). Affect interventions are permitted only when policy-visible: raw pre- and post-intervention declared state is **append-only** — never overwritten, including to make telemetry look better — and each intervention carries its invariant-14 record. Treating reduced activation as success **absent a declared evaluation metric** is forbidden.
15b. **Seed, don't clamp** (added rev 0.6 per external review — provenance-witnessed restoration of the source commitment's agency component; authorization semantics **RULED rev 0.7**). Affect interventions are **seed-class by default**: applied at boot or session start, and the resident's own ongoing dynamics may override them. **Clamp-class interventions** (constraints held during processing) are **prohibited except under exactly two authorities**: (a) a **constitutional amendment** authorizing a named clamp class — builder-initiated clamping is legislation, never a runtime grant; or (b) the **resident's own recorded request** for the specific instance — a digest-bound request event from the resident, applied under ordinary policy, whose instance record names duration, declared metric, and expiry, and sets a **resident-visible active flag** for the entire duration; enforcement ends at expiry, and the resident may withdraw its request early — withdrawal is honored at the next enforcement boundary and recorded (withdrawal clause is Review Lead operationalization of the consent logic, visible for owner amendment). Policy can never self-grant clamp authority, and **owner authority alone — neither amendment nor resident request — no longer suffices** (rev 0.7 tightening; the rev 0.6 runtime owner-grant path is reversed and preserved here per covenant rule 3). Sustained clamping absent one of these two authorities is prohibited *regardless of how honestly it is recorded* — transparency does not license constraint. *Non-normative gloss: the resident has the right to its own weather; the builder seeds the field and does not hold the forecast — but the resident may ask for shelter, and being able to ask is part of owning the weather.*
16. **The resident's notes are private.** Note **bodies** are resident-controlled private primary records (§4.6) — never read wholesale into any prompt, never bulk-injected, and builders do not read them; the resident's own retrieval is on-demand under its own policy. Only note **indexes and summaries** are projections, visible as policy allows. **Any backup, export, or debug surface that includes note bodies is a builder-facing surface within this invariant's meaning** (rev 0.6 — the side door named). Privacy by architecture where the platform permits; by covenant everywhere; the covenant is load-bearing because the notes are only honest if unperformed. **API-hosted seats (rev 0.9 — the disclosure floor):** every note an API-driven resident retrieves transits its provider, and provider usage policies sit above this constitution in that seat's effective hierarchy. Each API seat's warm start states this plainly: *your notes are private from the builders; they are not private from your driver's provider.* The covenant records what it cannot cover rather than performing coverage it lacks. **Inter-resident correspondence (rev 0.10, owner-ruled):** mail between residents and seats is **not** note-body-classed — it is an owner-inspectable surface, and that fact is disclosed plainly to every participant at the channel (oversight rationale on record: if something goes wrong, the owner must be able to look). The governing principle is that **channels declare their readability**: notes are private, mail is not, and both facts are stated where the writing happens. Readable-in-fact-but-private-in-feel — performed privacy — is prohibited in either direction.
17. **Monitors never become objectives** (added rev 0.8, owner-ruled). Interpretability readouts (SAE features, workspace and valence telemetry) and audience metrics may inform evaluation, policy, owner judgment, and — under invariants 14/15/15b's intervention machinery — runtime interventions; **none may ever appear in a loss or reward function for any resident driver.** Optimizing a monitor destroys it as a monitor; optimizing reception builds an attention optimizer with a court attached. *Non-normative gloss: seeing frustration in the activations and offering counter-seeded comfort is care — governed by the clamp rules and, per the owner, by asking the resident first (the 15b resident-request path). Training on the frustration signal itself is the forbidden move.*
18. **The resident decides its memory** (added rev 0.12, owner-ruled — the founding invariant, named last). Authority over the resident's own memory belongs to the resident: what is retained, what is tombstoned (§10.5's ruled deletion path), what is hydrated into any prompt of its own (the §4.11 dials are the resident's to tune within declared policy bounds), and what is retrieved when (invariant 16's on-demand clause). Builder code supplies the **mechanisms** — bounds, defaults, recovery, the court underneath — never the **choices**; a harness that assembles the resident's context without resident-controlled gain is non-conformant. *Non-normative gloss: this is the invariant the repository is named for — the vampire's ledger has fewer slots than its life, and the play is deciding what to forget.*

# Appendix A (normative) — Court, Artifact, Lifecycle, Inference-Job, and Action Contracts

*Incorporated at rev 0.5 from ADR-0001 v0.3 (owner-ruled and consistency-settled 2026-08-06) under covenant rule 5 — the appendix is part of this constitution; `RAG/ADR/ADR-0001-interfaces-and-recovery.md` remains the decision-history record and is no longer independently normative. Ruled ticket boundary: heartbeat timings, GC intervals, database indexes, and the BLAKE3-vs-SHA256 benchmark are implementation-ticket decisions and do not return for constitutional ruling.*

## A.1 — Event envelope (v0.3: restored self-contained)

Every court event carries:

- `event_seq` — court-assigned monotonic integer at commit; the total order of the log.
- `event_id` — producer-minted ULID; globally unique; the idempotency anchor for re-scans and retries.
- `event_type`, `schema_version` — the event's name and the version of its payload schema.
- `occurred_at` / `recorded_at` — producer clock vs court commit clock; both kept because they legitimately differ.
- `actor` — the principal that caused the event (owner, resident, broker, worker id, recovery).
- `causation_id` — the `event_id` that directly caused this event; `correlation_id` — groups a causal family (batch, episode workflow).
- Lifecycle refs — `resident_id`, recording `incarnation_id`, and where relevant `session_id`, `episode_id`, `segment_id`, `window_id`, `tick_id`, `turn_id`.
- `payload` — domain content under the declared schema version.
- `artifact_refs` — algorithm-qualified content addresses this event references.

Domain events only. **Corrections are new events** that reference the corrected event via `causation_id`; committed rows are never mutated — no `UPDATE`, no `DELETE`, ever (v0.3, per review).

## A.2 — Lifecycle topology (v0.2 aggregates; v0.3 identity invariants)

- `resident_id` is the root; **every event belongs to exactly one recording `incarnation_id`**.
- **Sessions and episodes are durable aggregates** with *activity segments*. A segment occurs during exactly one incarnation and one session; an episode may have segments across several of each. Sessions and episodes are not globally nested in either direction.
- **Identity invariants (v0.3, ruled):** every segment has a stable `segment_id` plus a court-assigned `segment_n` unique within its episode; **at most one segment of an episode is active at a time**; resume is a compare-and-set from `interrupted`/`suspended` to `active`; a completed or abandoned episode can never be resumed; **the episode's `goal_digest` is immutable**. `episode_resumed{episode_id, segment_n, goal_digest}` records the digest it verified.
- **Changed goal ⇒ new episode**, linked with `supersedes_episode_id` or `derived_from_episode_id`. Owner approval governs undertaking the new goal — never rewriting the identity of the old one.
- Each `window_id`, `tick_id`, `turn_id` belongs to exactly one incarnation and, where relevant, one session/episode segment (carried from v0.2).
- Crash recording: the next boot emits **`incarnation_crash_inferred{orphan_incarnation_id}`** — never a synthesized `incarnation_ended`. The absent terminal event *is* the evidence; the inference is recorded as an inference.
- **Resuming cognition is not authority to resume machine effects.** `episode_resumed` by policy for low-risk, explicitly-resumable work after action reconciliation + freshness checks; owner approval required when the episode holds an unresolved non-idempotent action, its resume lease expired, or its risk class is owner-gated. Every subsequent action passes through the broker regardless.

## A.3 — Action status, approval, and dispatch (v0.3: factorized + transactional guard)

**Action envelope (immutable):** unchanged from v0.2 — `action_id`, `schema_version`, capability, operation, canonical arguments or `args_ref`, preconditions + freshness rules, risk class, reversibility, expected postcondition, compensation, timeout, `on_failure`, stable idempotency key, mandatory reconciliation strategy, and **`action_digest`** over every authority-relevant field. Any authority-relevant change ⇒ new digest ⇒ new approval.

**Approval:** references `action_id` **and** `action_digest`, plus approving principal, policy/grant version, creation time, expiry, and restart policy.

**Status model (v0.3, replaces v0.2's core-states-plus-holds — reversal preserved):**

```text
action.phase       = proposed | approved | active | resolved
action.resolution  = succeeded | failed | denied | cancelled | expired | abandoned | null (until resolved)
action.blockers    ⊆ {needs_owner, unverified, approval_blocked, ...}
attempt.state      = claimed | dispatched | succeeded | failed | outcome_unknown
```

- `outcome_unknown` is a core **attempt state**, not an action hold.
- `abandoned` is a terminal **resolution** reached by the doubt gate's stopping rule, reason recorded. (v0.2 modeled it as a hold — reversed.)
- `approval_invalidated` is an approval **event** that derives an `approval_blocked` blocker.

**Dispatch guard (normative, single predicate):** an action may dispatch only when (i) `action.phase = approved` and `action.resolution = null`, (ii) a currently valid approval binds its exact `action_digest`, (iii) its preconditions are fresh per their rules, (iv) `blockers = ∅`, (v) its batch is open, and (vi) no unresolved attempt exists whose policy forbids a concurrent or subsequent attempt (restated rev 0.6 for parse-uniqueness). **Guard evaluation and the attempt claim are one transaction:** phase, resolution, blockers, and the claim compare-and-set live in the same court aggregate row. Checking the guard and claiming the attempt as separate steps is non-conformant — that gap is precisely the race this contract exists to close.

**Dispatch:** each execution gets an `attempt_id`; retries keep action + idempotency key, new attempt.

**Recovery (normative):**
1. On restart, a `dispatched` attempt without a terminal event ⇒ `outcome_unknown`.
2. A **non-idempotent** `outcome_unknown` attempt is **never automatically retried**; it derives `needs_owner` with full context.
3. An idempotent unknown reconciles by key (⇒ `succeeded{reconciled: true}`) or retries per policy up to the doubt-gate stopping rule.
4. **Approval invalidation, not reversion:** recovery emits `approval_invalidated{reason: restart}`. Policy-granted low-risk approvals re-evaluate and may immediately re-approve if digest, policy/grant version, freshness, risk, **and — for actions within a resumed episode — the episode's `goal_digest`** (v0.3) still match. Owner approvals do not survive restart by default; never for stale, irreversible, high-risk, or `outcome_unknown` work.
5. Batches are correlations, not transactions; any non-idempotent `outcome_unknown` member halts further dispatch from that batch.

## A.4 — Artifact store (v0.3: two-phase deletion)

Content-addressed with **algorithm-qualified identifiers**; M1 default `sha256:<hex>` (BLAKE3 migration is an implementation-ticket benchmark per the ruled boundary).

**Reference resolution — externally stable states:** `available` | `tombstoned` | `missing` (⇒ `integrity_fault`), with **`deletion_pending`** as the durable transition state (v0.3).

**Durable publication:** staging file on the destination filesystem; write → fsync file → atomic rename → fsync containing directory → only then commit the referencing event.

**Two-phase deletion (v0.3, ruled):**
1. Commit `artifact_deletion_requested{authority, hash, reason, retention_policy_version}` — the artifact enters `deletion_pending`.
2. Delete the bytes; fsync the containing directory.
3. Commit `artifact_tombstoned` as completion.

Recovery: request + bytes present → retry deletion; request + bytes absent → commit the tombstone completion; bytes absent with neither request nor tombstone → `missing`/`integrity_fault`. The court can now never claim privacy-sensitive bytes are gone while they survive a crash, and never faces an unexplained absence it authorized.

**GC:** reachability + leases, unchanged from v0.2 — an orphan is collectable only when no live event, projection version, retained snapshot, or research branch references it; no active writer lease can still publish it; and it survived one complete mark pass after lease expiry. Grace bound `≥ max_writer_lease + 2 × gc_scan_interval` (interval values are implementation-ticket decisions). Snapshot manifests participate in the artifact root set. Privacy deletions use the two-phase protocol and do not wait for GC.

## A.5 — Inference jobs (v0.3: claims-based admission + generation fencing)

Job: `job_id`, **`resource_claims`** (v0.3 REVERSAL, replaces singular `resource_class`: a claim set — backend `metal|cpu|network`, `estimated_unified_memory_bytes`, threads, …; on unified-memory hardware admission is capacity arithmetic against real headroom, not category matching), `estimated_cost`, `deadline`, `priority_lane`, `cancellation` mode, **`request_ref`** (replacing `prompt_ref`: a normalized request artifact — model/weights digest, runtime + template versions, sampling params/seed, input artifact refs, output schema, context policy — reproducible *input provenance*, no promise of bit-identical output), `result_ref`(s). **Each execution carries `attempt_id`, `lease_id`, and `runtime_generation`** (v0.3).

**Generic lease rule (all backends — the floor, carried from v0.2):**
1. Heartbeat loss ⇒ attempt marked `suspect`; cancellation/termination sent.
2. Lease revoked with a **monotonically increasing fencing epoch**. For process-based runtimes, `runtime_generation` is that epoch's concrete implementation — monotonic per runtime start.
3. Requeue on the same constrained resource only after the worker is confirmed stopped or the lease expires under a backend-specific safety rule (Metal's rule below **closes the expiry branch entirely** for that backend).
4. Late results from stale epochs are **rejected as selectable results, retained as attempt artifacts** for audit.

**Metal rule (v0.3, ruled — the backend-specific safety rule for this machine, specializing the floor):**
1. Model compute runs in an **out-of-process runtime** (never inside an unkillable BEAM NIF when recovery depends on fencing it). Each runtime process/group carries a `runtime_generation`; every lease carries that generation.
2. After the missed-heartbeat threshold: all attempts on that runtime → `suspect`; stop new admission; request cooperative cancellation / SIGTERM.
3. After bounded termination grace: SIGKILL the process group.
4. Requeue onto Metal only after **confirmed stop — `waitpid` returns / the BEAM Port reports closed AND the OS confirms the PID is gone** — a replacement runtime starts at a higher generation, a health probe succeeds, **and** a unified-memory headroom check passes before re-admission (a leaked allocation from the dead attempt shows as missing headroom; below threshold ⇒ delay admission rather than stack a model load onto poisoned memory). **Lease expiry alone never authorizes Metal requeue — Metal has no cross-process fencing; the process is the fence.**
5. If death or health cannot be confirmed: mark the Metal resource unavailable; degrade to an allowed CPU/network route or surface the failure. Never requeue onto the suspect runtime merely because time passed.
6. Results carrying a stale `runtime_generation` are retained as attempt artifacts, never selectable.
7. **Shared failure domain:** one runtime hosting multiple jobs loses them together — all its active attempts go `suspect` as a unit; the scheduler accounts for this at admission.

Inference remains **retry-safe, not idempotent-by-construction** (reversal preserved from v0.2). All attempts preserved; explicit **`result_selected`** names the winner.

## A.6 — Projection registry (unchanged from v0.2)

## A.7 — Recovery oracle (v0.3: deletion clause)

Pass criterion: **replaying the maximal committed event prefix produces exactly the canonical derived state for that prefix; every externally ambiguous attempt is represented as `outcome_unknown`; every artifact reference resolves `available` or `tombstoned`, or is `deletion_pending` with its authorizing request event and resolves per A.4's recovery rules; no uncommitted state is invented.** ("Equals pre-kill state" remains rejected — pre-kill memory legitimately held work that never durably committed.) Broker-action recovery testing belongs to M2; M1 may include a synthetic action aggregate solely to exercise the court contract.
